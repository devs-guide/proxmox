# GitHub release publication policy

This policy applies to every GitHub release page in this repository: existing
releases and all future releases. Release tags and their source commits remain
immutable. A release title or body may be corrected in place after human
review, provided the tag, target commit, and assets are not silently changed.

## Human review gate

The exact proposed release title and complete Markdown body must be presented
for human review before any `gh release create`, `gh release edit`, or web UI
publication action changes GitHub.

- Create new releases as drafts unless the reviewer explicitly authorizes
  immediate publication.
- Do not publish, un-draft, or edit an existing release from an unreviewed
  generated summary.
- After approval, use the reviewed Markdown as a notes file without rewriting
  it during publication.
- Verify the live page through the GitHub API after publication or editing.
- Confirm the tag object, target commit, draft/prerelease state, and asset list
  still match the reviewed intent.

## Required release structure

Use [`template.md`](template.md). Every release body must contain:

1. `## X.Y.Z`
2. One or two plain-language summary paragraphs
3. `### Scope`
4. `### Highlights`
5. `### Added`
6. `### Changed`
7. `### Fixed`
8. An operator workflow or safety section when the release changes a
   privileged, destructive, network, authentication, or storage operation
9. `### #COMMIT`
10. `### Notable commits since <previous-tag>`
11. `### Assets`

If a required change category has no entries, write `None` rather than
omitting its heading.

The GitHub release title should use `X.Y.Z — Concise Feature Name`. Keep the
repository's bare numeric tag format; do not add a `v` prefix unless the tag
policy is separately changed and approved.

## Content requirements

- Explain what changed, why it matters, and how an operator experiences it.
- Describe reusable project behavior. Do not make one hostname, IP address,
  disk count, account, chassis, or other local request the release narrative.
- Local acceptance may be summarized as validation evidence only when it adds
  confidence to the general feature. Remove credentials and private evidence.
- Keep `Scope` explicit about the release range, feature boundary, published
  entrypoints, and important exclusions.
- Use `Highlights` for the highest-signal operator-facing changes.
- Use `Added`, `Changed`, and `Fixed` for behavior and intent rather than raw
  diff statistics.
- Identify important publication, runtime, compatibility, and safety fixes.
- List notable commits with abbreviated hashes and their exact commit
  subjects. Do not dump every mechanical or low-signal commit.
- State whether binary assets exist. Source archives generated by GitHub and
  Pages-published scripts should be described accurately.
- Never claim that source-only documentation is published on Pages.

## Required source review

Before drafting a release:

1. Read at least one prior well-structured release page for tone and layout.
2. Inspect the complete previous-tag-to-candidate commit range.
3. Review the diff summary and all operator-facing files.
4. Confirm every runtime dependency is included in the Pages publication and
   validation graph.
5. Confirm the proposed notable-commit list against the actual commit range.
6. Store the proposed body in a regular Markdown file for review and use that
   exact file for GitHub publication.

## Retroactive release reconciliation

Before publishing a new release, audit every previously published release page
against this policy. Any historical page missing the required structure,
general project framing, or notable commit history must receive its own
human-reviewed replacement body before the new release is published.

Historical cleanup changes only the GitHub release presentation. Do not move
or recreate its tag, change its source commit, add or delete assets, or rewrite
the historical implementation. Verify those invariants after every edit.

## Publication checklist

- [ ] Previous tag and candidate commit are exact and reviewed.
- [ ] Historical release pages have been reconciled with this policy.
- [ ] Proposed title follows `X.Y.Z — Concise Feature Name`.
- [ ] Complete body follows the required template.
- [ ] Local-machine details are not the main release narrative.
- [ ] Notable commits use verified hashes and exact subjects.
- [ ] Published runners and dependency claims match the Pages graph.
- [ ] A human approved the exact title and body.
- [ ] New release was created as a draft unless immediate publication was
      explicitly approved.
- [ ] Live GitHub release was verified after creation or editing.
- [ ] Tag object, target commit, release state, and assets remain correct.
